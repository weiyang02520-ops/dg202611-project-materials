**状态：CURRENT / INTERNAL GOVERNANCE**  
**用途：长期内部最高工作规则，用于统筹正式方案书、开发、文献、实验与独立审计。**  
**注意：本文件不是提交给官方的正式方案书。**

---

## 0. 核心定义

DG-202611 从现在起严格区分四类东西：

1. **正式提交方案书（OFFICIAL SUBMISSION）**  
   给官方评委看的正式答卷。描述完整技术方案、系统架构、方法、已有真实基础、实验设计与最终实验结果。  
   不写内部开发进度、TODO、PASS/FAIL、审计 issue、成熟度等级、任务分工。

2. **项目开发计划书（DEVELOPMENT PLAN）**  
   内部执行文件。记录当前做到哪里、还缺什么、下一步开发什么、如何验证、需要什么证据、什么时候算完成。

3. **证据与实验库（EVIDENCE / EXPERIMENTS）**  
   保存代码提交、仿真、实机、CSV、bag、日志、截图、照片、指标计算、失败案例、复现实验等。

4. **独立外部审计（EXTERNAL AUDIT）**  
   独立检查正式方案书与开发证据，不直接改任何东西。审计结果返回 MASTER，由 MASTER 裁决后分派整改。

**四者不得混写、不得互相替代。**

## 1. 正式方案书到底是什么

正式方案书不是“今天已经开发到哪里”的汇报。

它的任务是：

> 按照官方比赛要求，设计并论证一套最终能够完成比赛任务的完整系统。

因此，只要某项技术已经由老师 / 项目明确确定纳入最终系统，就可以在正式方案书中按正式系统组成写，不因为当前代码尚未完成就降级成“未来可能”“计划考虑”。

### 例：UWB

正式方案书可以写：

> 本系统采用 UWB 提供局部绝对定位观测，并结合覆盖状态、NLOS 条件及观测质量动态决定其参与、降权或拒绝融合。

不能因为当前仓库尚无 UWB 代码，就把 UWB 从正式技术方案中删除。

但不能无证据写：

> 当前样机已经完成 UWB 融合部署。  
> 实测 UWB 定位误差为 XX cm。  
> 实验表明 UWB 使误差降低 XX%。

除非这些事实后续真的产生了项目证据。

## 2. 正式方案书与开发状态必须分开判断

### 2.1 方案设计事实

已经确定进入最终系统的技术，可以按“设计态现在时”写：

- 本系统采用……
- 系统通过……
- 模块负责……
- 观测进入……
- 系统根据质量状态进行降权或拒绝……

### 2.2 已实现 / 已验证事实

只有存在一手证据时才可以写：

- 已完成集成
- 已部署
- 已在 Gazebo 验证
- 已在实机验证
- 实测达到 XX
- 成功率 XX%
- 定位误差 XX cm

### 2.3 正式提交稿禁止出现的内部内容

禁止在正式方案书中出现：

- Package A
- S01/S08 等内部场景编号（除非最终整理成正式实验编号）
- PASS / FAIL
- TODO
- 当前完成度百分比
- A/B/C/D/E 成熟度
- 内部审计 issue ID
- “下一步开发……”
- Claude / Codex / ZCode / DSH 等 AI 工作线
- Git dirty、commit gate 等内部项目管理信息

这些全部留在内部开发与证据材料中。

## 3. “已有基础”与“最终方案”的边界

正式方案书可以介绍真实存在的项目基础，用于证明方案具备实施条件，例如：

- 已有机器人样机
- 已有计算平台
- 已有 LiDAR / IMU / GNSS-RTK / ZED 等真实硬件
- 已有 ROS2 工程基础
- 已有真实存在的驱动、导航、定位或算法模块

但“已有基础”必须是真的。

如果某项技术属于最终系统但当前尚未部署：

- 可以在总体方案 / 技术路线 / 系统架构中正常作为最终系统组成写；
- 不可以在“已有基础”章节中冒充已经部署完成。

## 4. 性能指标写法

### 4.1 总原则

DG-202611 属于“先写方案书，再持续开发和验证”的项目。

因此正式方案书必须围绕官方要求反推技术方案，而不能只按今天已有代码写。

### 4.2 默认性能论证链

以后关键指标默认采用：

> **高水平最新文献成绩 → 对应技术条件 → 本方案采用的技术路线 → 具备达到官方目标的技术基础 / 可行性**

例如：

> 相关研究在 XX 条件下已实现约 18 cm 定位精度。本方案采用相近的多源融合与误差约束机制，因此具备达到比赛平面定位误差小于 20 cm 指标的技术基础。

优先于直接写：

> 本项目已经达到 18 cm。

### 4.3 可以“写强”，不能“造证据”

允许：

- 强调方案优势
- 强调先进性
- 表述“具备达到比赛指标的技术基础”
- 在文献充分支撑时写“可实现 / 可达到”类方案级判断
- 积极表述最终系统能力

禁止：

- 编造不存在的测试
- 编造项目实测数字
- 编造截图、曲线、日志
- 编造论文或论文数字
- 把文献结果写成项目自己的实验结果

### 4.4 如果官方指标高于公开 SOTA

如果顶刊、顶会或顶尖实验室在公开条件下都无法支撑官方要求：

- 不允许凭空声称本项目已经能做到；
- 以最新可靠高水平文献的真实能力边界为技术上限；
- 官方指标仍作为项目目标；
- 通过技术组合、改进设计、约束条件和后续实验说明努力方向；
- 不写明显超过可靠文献上限的无证据性能。

## 5. 信息优先级

### 5.1 技术内容 / 性能判断

按本项目当前约定：

1. 最新、可靠、高水平文献 / 顶刊顶会 / 顶尖实验室公开结果
2. 官方比赛技术要求
3. 老师明确口径
4. 已确认的最终技术方案
5. 当前开发状态

解释：

- 官方要求决定“我们要回答什么、目标是什么”；
- 最新高水平文献决定“技术上能说到什么程度、性能上限能否站得住”；
- 不能为了迎合官方指标而声称超过公开可靠技术边界。

### 5.2 格式 / 提交规则

官方最高优先级：

1. 官方模板 / 官方格式 / 官方字数 / 官方附件与提交要求
2. 官方没有规定的部分，采用正规的科研 / 技术方案书格式
3. 优秀学长案例仅用于版式、结构、图表和专业呈现参考

不得复制学长案例中的：

- 团队身份
- Logo
- 项目名
- 作者
- 学校
- 联系方式
- GitHub
- 任何不属于 DG-202611 的内容

## 10. DSH 写作审查机制

DSH 不得连续自行写完全书。

流程：

`MASTER 定义任务 → DSH 成稿 → MASTER 审查 → 决定 PASS / 小修 / 重写 / 补文献 / Codex专项审 / ZCode专项查 → 再进入下一轮`

审查颗粒度不机械规定。

- 稳定章节：可以按章审
- 高风险章节：下钻到小节审
- 性能、实验、引用、高程、重定位等高风险内容提高审查频率

## 12. 审计必须拆成两种判定

### 12.1 OFFICIAL_PROPOSAL_AUDIT

只站在官方评委角度检查：

- 官方格式是否满足
- 官方要求是否回答完整
- 技术路线是否合理
- 文献是否足够新、足够强、引用正确
- 性能表述是否站得住
- 是否把文献结果冒充项目实测
- 是否存在明显技术硬伤
- 图表、引用、格式是否正规
- 是否包含不该给官方看的内部信息

**不得因为当前代码尚未实现某项最终方案，就直接要求从正式方案书删除该技术。**

### 12.2 DEVELOPMENT_EVIDENCE_AUDIT

检查：

- 代码有没有
- Git 是否可追
- 仿真有没有
- 实机有没有
- 实验结果能否复现
- CSV / bag / 截图是否真实
- 指标是否真的达到
- 失败记录是否完整
- evidence provenance 是否可靠

两套审计可以得出不同结论，这是正常的。

例如：

`UWB = VALID_FINAL_SYSTEM_DESIGN`

同时：

`UWB_RUNTIME_IMPLEMENTATION = NOT_YET_VERIFIED`

两者不冲突。

- 图 / 表 / 编号
- 实验结果
- 是否有内部痕迹
- 是否有 AI 式自证
- 是否存在无证据实测声明
- 是否存在明显超过可靠文献边界的吹法

最终开发审计问题不直接倒入正式方案书；只修那些真正影响官方答卷可信度的问题。
